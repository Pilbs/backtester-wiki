Forex Backtester

Roadmap

North Star

Take an existing automated strategy, test it over deeper historical data, sweep the important parameters, and understand whether the result is robust.

The roadmap should be judged against that sentence. Features that do not help strategy research should not distract the project.

Done — Historical Data Foundation

  • OANDA candles stored in Cloudflare D1.
  • BID / ASK / MID OHLC.
  • Native EUR/USD M1 and M5 proven end-to-end.
  • Reusable data reader and import pipeline.

Done — Human Backtesting V1

  • Realistic multi-trade account/execution engine.
  • Strategy definitions and validated configuration.
  • Common indicator toolkit.
  • Generic parameter grids and run limits.
  • Dataset loaded once per experiment.
  • Structured schema-v5 experiment JSON.
  • Year/month summaries, drawdown and causal MFE/MAE diagnostics.
  • Real six-run ORB acceptance experiment passed.

This milestone is closed. Do not keep adding speculative engine features unless a real strategy exposes a generic missing capability.

Next — Research Platform V1

The purpose of this milestone is simple: make the engine easy for a human to use.

Phase 1 — Generic Research Config

Create one obvious research.config.js containing universal market/account/execution settings plus the selected strategy's own config and parameter grid.

The user should not have to edit orb-sweep.js or know the application plumbing.

Phase 2 — Strategy Registry + Discoverability

Add a central strategy registry so strategy: "orb" resolves to the correct definition. Expose common account/execution choices as metadata so the available options are discoverable rather than hidden in validators.

Phase 3 — Generic Runner

Add one command:

npm run research

It should validate the config, show the requested combination count, run the experiment, print progress/results and write JSON.

Acceptance test: reproduce the current ORB smoke experiment from the generic config without touching ORB-specific experiment code.

Phase 4 — Minimal Human Web UI

Build a research UI, not a visual strategy builder. The browser should let the user choose strategy, market, dates, account assumptions and parameter values, preview the run count, launch research and inspect ranked results.

Strategy-specific fields should be generated from the chosen strategy definition rather than hard-coded into the UI.

Phase 5 — Job/Persistence Boundary

Add asynchronous job handling and saved experiment metadata only as required by the real browser workflow. Long experiments should not rely on one HTTP request staying open.

Pine parsing removes ingestion friction; it is not the product itself. Start with a supported subset rather than promising arbitrary Pine compatibility.

Later — AI Researcher V1

The AI should orchestrate deterministic platform tools such as:

plan_experiment
run_experiment
compare_runs
inspect_trades
analyse_periods

The agent forms hypotheses and requests experiments; the backtester remains responsible for deterministic calculations.

Later — Productisation

Auth, plans, billing, broader instrument coverage and scale come after the human research workflow proves useful. A curated set of deep, clean instruments is acceptable; the product does not need TradingView's market catalogue.

Next Session — Concrete Actions

  1. Start a new milestone/branch for Research Platform V1.
  2. Agree the exact shape of research.config.js.
  3. Add a strategy registry.
  4. Centralise discoverable universal config metadata.
  5. Build npm run research.
  6. Reproduce the accepted ORB smoke run through that generic path.
  7. Only then sketch the minimal browser UI over the same model.
