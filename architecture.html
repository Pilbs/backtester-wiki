Current Folder Model

src/
  account/       account config, state and position sizing
  backtest/      runner, service, context, execution policy, summaries, analytics
  data/          OANDA/D1 access and historical import
  experiments/   current human/reference experiment scripts
  indicators/    generic calculations used by strategies
  market/        instrument/timeframe metadata
  reporting/     console and JSON output
  research/      parameter grids, planning, sweeps and high-level experiments
  strategies/    generic contracts + strategy folders
    orb/          ORB implementation and definition
  time/          timezone/session helpers
  tests/         deterministic and integration tests

Responsibilities

LayerKnows about
DataHow historical market candles are stored/retrieved.
MarketInstrument facts such as pip size and fixed timeframe duration.
Indicators/TimeReusable calculations and session/timezone helpers.
StrategyTrading decisions, state and strategy-specific parameters.
AccountCapital, sizing, equity, leverage, margin and risk constraints.
BacktestDeterministic order/fill/trade simulation and run results.
ResearchParameter combinations, experiment planning and repeated runs.
ReportingHow results are presented/saved.

The Important Separation

Universal configuration
  market / account / execution / research limits

Strategy-specific configuration
  owned by the selected strategy definition

This is why one generic runner and future web UI can support strategies with completely different parameter sets.

Where the Product Layer Goes

                 Human Web UI
                      |
                      v
            Research Platform layer
             /                 \
     config / jobs        saved results
             \                 /
                      |
                      v
             Human Backtesting V1

Later Pine translator ----^---- Later AI researcher

The web UI should call a clean research layer. It should not directly coordinate D1, account state and runner internals.

Guiding Rule

If a capability could be useful to many strategies, build it generically. If it describes how one strategy behaves, keep it inside that strategy.

A second rule now matters just as much: make the existing engine easier to use before making the engine itself more complicated.
