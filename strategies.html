Strategy Development

A Strategy Has Two Pieces

This is the key concept for understanding why different strategies can still use one generic research platform.

1. Runtime strategy

The runtime contains the actual trading rules and state:

{
    name: "My Strategy",
    reset() { ... },
    onCandle(context) { ... }
}

2. Strategy definition

The definition describes the parameter catalogue that a human, runner or future UI is allowed to configure:

{
    id: "ema-cross",
    name: "EMA Cross",
    version: 1,
    createStrategy,
    parameters: {
        fastLength: { type: "integer", default: 20, min: 1 },
        slowLength: { type: "integer", default: 50, min: 2 }
    }
}

Parameter types currently supported are number, integer, string and boolean. Definitions can also specify defaults, required fields, min/max, options and sweepable: false.

Why the Definition Matters

ORB and an EMA/ATR strategy do not need the same fields. That is fine. The generic experiment only selects a strategy ID; the chosen definition tells the platform what parameters exist and validates them.

research config
   strategy: "orb"
         |
         v
ORB definition
         |
         +--> valid fields
         +--> defaults
         +--> min/max/options
         +--> creates ORB runtime

Later, the web UI can use exactly the same definition to generate strategy-specific form controls dynamically.

What the Strategy Can See

context.candle
context.index
context.instrument
context.timeframe
context.account
context.position
context.openTrades
context.pendingOrders
context.getCandle(offset)
context.getRecentCandles(count)

The current strategy candle is complete before the strategy sees it. Future-candle access is blocked. MID prices are normally used for chart-style signal calculations.

What the Strategy Can Ask the Engine To Do

A strategy returns null, one instruction, or an array of instructions.

Actions:
ENTER
EXIT
UPDATE_STOP
UPDATE_TARGET
CANCEL_ORDER

Order types:
MARKET
LIMIT
STOP
STOP_LIMIT

Time in force:
GTC
DAY
IOC
FOK

Entry sizing can be UNITS, CASH, PERCENT_EQUITY or RISK_PERCENT. Stops/targets can be expressed as PIPS, PRICE or PERCENT. Exits can target ALL, TRADE_ID, ENTRY_ID or SIDE, and partial exits can use UNITS or PERCENT_POSITION.

Common Indicator Toolkit

Reusable indicators live under src/indicators/. Current helpers include SMA, EMA, RMA/Wilder, ATR, RSI, rolling highest/lowest, rolling standard deviation, true range, crossover/crossunder and confirmed pivots.

Stateful indicators expose:

indicator.next(value)
indicator.reset()
indicator.value

Strategy-specific calculations remain strategy-side. The engine should receive executable instructions, not concepts such as "ATR stop".

How to Add a New Strategy Today

  1. Create src/strategies/my-strategy/my-strategy.js.
  2. Create my-strategy-definition.js describing every configurable/sweepable parameter.
  3. Use common indicator/time helpers where they fit.
  4. Reset all strategy/indicator state in reset().
  5. Return generic trade intents from onCandle().
  6. Add a deterministic strategy test.
  7. Run npm test.
  8. Run a small real-data smoke test before a large sweep.

For a TradingView strategy today, this is a manual Pine-to-JavaScript port. That is acceptable for the current personal tool; automated Pine ingestion is a later milestone.

What Does Not Belong in Strategy Code

D1 queries
historical data loading
broker/API calls
fill simulation
spread/slippage calculations
commission/account calculations
margin calculations
experiment loops
result persistence

Those are generic platform responsibilities.
